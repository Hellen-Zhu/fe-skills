# Frontend Requirement Test Strategy Planner

## Goal

Turn an early requirement into a phase-aware frontend test strategy. Define business acceptance coverage before implementation, then identify which checks should later become unit, component, integration, E2E, visual, or contract tests.

## First Inspect

Before planning, inspect any available:

- PRD, story, acceptance criteria, screenshots, wireframes, and workflow notes
- roles, permissions, statuses, entry points, and state transitions
- API contracts, backend assumptions, or schema drafts
- existing quality gate docs or test matrices
- existing related features and test patterns if a repo is available

Do not assume final component names, selectors, routes, API clients, or stores before implementation exists.

## Phase Boundary

In pre-implementation planning:

- Define business acceptance cases and candidate layers.
- Design E2E at the business-contract level only.
- Mark unit/component/integration cases as candidates until code structure exists.
- Avoid selectors, component names, exact file paths, and implementation details unless provided.

In post-implementation planning:

- Revisit candidate layers against real code.
- Confirm what should be generated by unit, component, integration, visual, contract, or E2E skills.
- Downshift overly broad E2E cases to lower layers when code boundaries make that possible.

## Layering Principle

Use the lowest reliable layer that can prove the behavior:

```text
Pure rule -> unit
Single UI component behavior -> component
Page + route + store + API mock -> integration
Real deployed cross-role or cross-page flow -> E2E
Layout or appearance risk -> visual regression
Frontend/backend schema compatibility -> contract
```

E2E defined before implementation is a business acceptance contract, not a script-level automation plan.

## Planning Workflow

1. Extract actors, permissions, statuses, operations, entry points, and final outcomes.
2. Split positive and negative business scenarios.
3. Identify smoke cases that prove minimum deployability.
4. Identify regression cases that protect the full workflow and important failure modes.
5. Classify each validation point into a candidate test layer.
6. Mark quality gates for PR, release, nightly, or production smoke.
7. Record assumptions and open questions that affect test design.
8. Recommend the next skill to use.

## Output Format

Always produce:

- requirement summary
- roles and permissions
- state model or state transitions
- positive and negative acceptance scenarios
- smoke and regression candidate cases
- candidate test layer matrix
- quality gate recommendation
- assumptions and open questions
- next skills

Use concise tables when useful.

## Quality Gate Guidance

Mark as quality gates when the scenario protects:

- user cannot complete a core workflow
- unauthorized action becomes available
- status transition is wrong
- API contract is incompatible
- released UI cannot load critical pages
- production smoke fails

Do not mark every edge case as a blocking gate. Use priority and pipeline stage.

## Example Classification

For maker-checker Create Trade:

```text
E2E acceptance:
- maker creates trade -> Pending Approval
- checker approves -> Live
- checker rejects -> Draft
- checker cannot create trade
- maker cannot approve own pending trade

Candidate lower-layer coverage:
- unit: permission helpers, status transition mapper, payload builder
- component: New Trade button, row action menu, details action bar, reject dialog
- integration: create -> details, list approve/reject, details approve/reject, API failures
- visual: portal action menu, details pending/live/draft, validation layout
- contract: create/detail/approve/reject/error schemas
```

## Output Expectations

When finished, report:

- strategy artifact or summary
- candidate layer decisions
- E2E acceptance cases to lock before implementation
- implementation-dependent tests to revisit later
- recommended next skill
